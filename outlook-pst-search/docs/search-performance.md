# 검색과 답변 성능 확인

## 1. 구간별 계측

Windows 기본 로그는 %LOCALAPPDATA%\OutlookMailSearch\app-runtime.log입니다. --data로 데이터 폴더를 지정한 경우 해당 폴더를 사용합니다.

```powershell
$searchLog = Join-Path $env:LOCALAPPDATA 'OutlookMailSearch\app-runtime.log'
Select-String -Path $searchLog -Pattern 'Search profile' | Select-Object -Last 30
```

로그의 같은 id로 검색과 원본 확인을 연결합니다. phase=query는 최초 검색, phase=verify는 원본 확인, phase=answer는 로컬 생성, phase=intranet_answer는 사내 즉시 답변 요청입니다. phase=preview와 phase=external_answer는 검토용 발췌 및 검토 후 생성 요청입니다. rewrite_ms는 질의 분해, followup_ms는 누락 진단과 동일 범위의 추가 검색 및 통합 재정렬, fts_ms는 키워드 검색과 결과 미리보기, embed_ms는 검색어 벡터 요청, vector_ms는 후보 조회와 비교, rerank_ms는 재정렬, access_ms는 실제 파일·폴더 접근 확인입니다. 답변 생성 경로에는 context_ms, generation_ms, validation_ms도 기록합니다. 병렬 구간과 겹치는 계측이 있으므로 구간을 더한 값은 전체 시간과 다를 수 있습니다. 검색어와 메일 내용은 계측 로그에 기록하지 않습니다.

동일한 검색어·보관함 범위를 사용하고 처음 실행과 반복 실행을 구별해 비교하세요. 공유폴더의 첫 확인은 검색과 별도 요청으로 실행됩니다. 원본 보관함을 병렬로 검사하고, 확인된 결과를 먼저 돌려줍니다. 응답 기한을 넘긴 경로의 검사는 백그라운드에서 완료되면 캐시에 반영됩니다. 최근 확인이 성공한 결과는 최대 10초간 재사용합니다. 원문·첨부 열기와 답변 API 전송 전에는 접근을 다시 확인합니다. 기존 API 호출은 두 번째 요청 없이 접근 확인까지 마친 결과를 돌려줍니다. 브라우저는 defer_access를 지정해 분리된 경로를 씁니다.

## 2. 합성 데이터 전후 비교

업데이트본의 tools\benchmark.py 한 파일을 양쪽 소스에 대해 실행하면 동일한 데이터 생성 코드를 사용합니다. Windows PowerShell에서 아래 두 경로를 실제 소스 폴더로 바꾸세요.

```powershell
$benchBefore = 'C:\work\before\outlook-pst-search'
$benchAfter = 'C:\work\after\outlook-pst-search'
$benchScript = Join-Path $benchAfter 'tools\benchmark.py'
foreach ($benchSource in @($benchBefore, $benchAfter)) {
    $env:PYTHONPATH = $benchSource
    py -3 $benchScript --count 1500 --chunks 35 --repetitions 12
    py -3 $benchScript --semantic-scope --count 25000 --dimensions 1024 --repetitions 10
    py -3 $benchScript --duplicate-attachments --count 64
}
Remove-Item Env:\PYTHONPATH
```

- 본문은 Common Korean terms의 중앙값과 P95를 비교합니다. 위 크기는 약 57,000구간입니다. --count 13922로 늘리면 약 53만 구간이 되며 임시 디스크 공간 사용량도 늘어납니다.
- 벡터는 작은 보관함과 큰 보관함 필터의 반환 건수 및 P95를 봅니다. 이 시험은 검색어 벡터를 고정해 Ollama와 재정렬을 제외합니다.
- 중복 제거는 전체 구간과 임베딩에 실제로 보낸 텍스트 수를 봅니다. 변환·임베딩 시간을 실제 모델과 비교하려면 운영 로그에서 같은 버전에 대해 측정하세요.
- 브라우저에서 **의미 검색 결과 재정렬**을 껐다 켜며 같은 검색어를 두 번씩 실행합니다. 두 번째의 embed_ms가 쿼리 캐시 적중 시 0에 가까운지, 재정렬을 켰을 때 rerank_ms가 추가되는지 비교합니다.

## 3. 선택 사항인 USearch

사내에서 검증한 해당 Python·Windows 아키텍처의 USearch·NumPy 및 필요한 의존성 휠을 오프라인으로 설치한 뒤 아래처럼 실행합니다. 기본 실행은 SQLite를 사용합니다. NumPy를 사용할 수 있는 환경은 후보 벡터 계산을 배열 연산으로 처리합니다.

```powershell
py -3 -m pip install --no-index --find-links C:\approved-wheels usearch numpy
.\start-windows.cmd --vector-index usearch
py -3 -m tools.benchmark --semantic-scope --count 25000 --dimensions 1024 --repetitions 10 --vector-index usearch
```

유효한 보관함·색인 버전·임베딩 모델·차원별 인덱스는 데이터 폴더의 `vectors`에 원자적으로 저장됩니다. 앱 재시작 후 첫 조회에서 메모리 매핑으로 엽니다. 캐시가 없는 보관함은 SQLite에서 백그라운드로 구축하고, 준비되기 전에는 SQLite 경로를 사용합니다. 교체·삭제된 보관함 버전의 파일은 정리합니다. 보관함은 인덱스 선택으로 제한하고 날짜·발신자 조건은 SQLite로 확인합니다. 후보를 더 가져와도 필터 결과 수가 부족하면 기존 SQLite 경로를 사용합니다. HNSW 후보의 최종 점수는 원래 float32 벡터로 계산합니다. 양자화 후 결과 재현율은 승인된 사내 질의로 별도 검증해야 합니다.

## 4. 회신과 인용 검증

메일은 인식한 답장 인용·서명 구간을 본문 색인에서 제외합니다. 원문 보기는 전체 본문을 사용합니다. 동일 첨부는 파일 종류와 바이트가 같으면 성공한 추출을 공유합니다. 공유 가능한 첨부 내용·파일명·위치가 같으면 메일의 제목·발신자·발송일에 관계없이 벡터도 재사용합니다. 리랭커와 답변에는 동일 첨부 구절의 대표 근거를 사용합니다. 임베딩 형식은 보관함별로 선택하므로 기존 벡터는 검색에 사용할 수 있고, 보관함 **갱신** 시 새 프리픽스로 점진적으로 전환합니다. 기존 보관함에서 **갱신**을 실행하면 파일이 그대로인 PST도 구형 색인이면 새 형식으로 처리합니다. 저장해 둔 EML이 있으면 재사용합니다. 잠겼거나 다시 읽을 수 없는 PST는 이전 색인으로 검색할 수 있으며, 다음 갱신 때 다시 시도합니다.

로컬 답변은 관련 부모·자식 회신과 인접 문맥을 더 가져온 뒤 모델에 발송 시각순으로 제공합니다. 인용은 공백과 줄바꿈 차이를 허용하고 화면에는 원문 표기를 제공합니다. 복수 출처가 필요한 문장은 각 독립 사실에 근거가 있을 때 통과합니다. 실제 메일로는 최종 승인·취소 구별, 주체·수량 일치, 출처 링크 열기, 근거 부족 시 보류를 기준으로 수동 검증할 수 있습니다.

## 5. 질문 필터와 로컬 답변 용량

- 메일 질문의 **최근**은 오늘을 포함한 30일이며, **이번 주**는 월요일부터 일요일, **지난달**과 **올해**는 달력 기준입니다. 날짜는 PC의 현지 시각을 기준으로 비교합니다. 기간 두 개를 비교하거나 날짜가 납기·업무 일정으로 읽히는 표현은 자동 적용을 피합니다. UI에 날짜를 하나라도 입력했다면 선택한 날짜 범위를 사용합니다.
- `발신자: 홍길동`, `name@example.invalid이 보낸`, **첨부가 있는 메일**을 메일 검색 범위에 반영합니다. **첨부파일 내용 요약**은 첨부 본문에 우선순위를 줍니다. 명시한 UI의 발신자·첨부 조건이 우선합니다.
- 로컬 `/api/answer`는 근거 최대 18개와 원문 인용을 붙인 항목 최대 8개를 사용합니다. Ollama 컨텍스트는 보통 8,192토큰을 쓰고, 근거량이 많으면 모델 한도 안에서 기본 상한인 16,384토큰까지 늘립니다. 모델 정보에 최대값이 없으면 8,192 이하를 사용합니다. 입력이 한도를 넘으면 순위가 높은 원문 구간을 통째로 남기고 후보를 일부 제외해 부분 답변으로 표시합니다.

```powershell
.\start-windows.cmd --answer-num-ctx 8192
```

환경 변수 `MAILSEARCH_ANSWER_NUM_CTX`로도 2,048~32,768토큰 사이의 상한을 지정할 수 있습니다. API 답변은 사용자가 검토한 발췌문을 선택된 입력 예산에 맞춰 전송합니다. 앱을 시작하면 `app-runtime.log`의 `Vector search backend=` 줄에서 선택된 벡터 백엔드와 NumPy 사용 여부를 확인할 수 있습니다. USearch가 로드된 경우 개별 보관함의 HNSW 준비 상태는 `Vector shard ready` 로그로 확인합니다.

## 6. 백그라운드 임베딩과 벡터 실행 계획

색인 중 한 번에 처리할 구간 수는 16~128개, 요청 타임아웃은 30~60초 사이에서 지정합니다. 기본 배치는 사내 API 64개, 로컬 Ollama 24개이며 기본 타임아웃은 60초입니다. 시간 초과, 연결 끊김, 재시도 가능한 HTTP 오류가 발생하면 같은 위치에서 절반 크기로 다시 요청합니다. 연결이 끊기거나 서버가 5xx를 반환하면 2초 대기합니다. 축소한 배치가 10회 연속 성공하면 설정값까지 단계적으로 크기를 두 배로 늘립니다.

임베딩 입력은 제어문자와 잘못된 유니코드를 제거하고 최대 2,400자로 정리합니다. 단건 오류 시 500자로 줄여 재시도합니다. 계속 거부되는 구간은 키워드 검색에 남기고 의미 색인에서만 제외하며, 진행률에는 처리한 구간으로 표시합니다. 연결 실패가 5회 연속 발생하거나 Ollama를 시작할 수 없으면 의미 색인을 중단하고 저장한 벡터를 보존합니다. Ollama가 종료되거나 응답하지 않으면 앱이 시작한 프로세스를 다음 요청에서 재기동할 수 있습니다.

파일명, 공백을 제외해 15자 미만인 구간, 문자나 숫자가 없는 구간은 키워드 검색에 남기고 임베딩 요청에서 제외합니다. 검색어의 임베딩 제한은 별도로 적용됩니다.

```powershell
.\start-windows.cmd --embedding-batch-size 32 --embedding-batch-timeout 60
```

환경 변수는 `MAILSEARCH_EMBEDDING_BATCH_SIZE`와 `MAILSEARCH_EMBEDDING_BATCH_TIMEOUT`입니다.

SQLite에서 벡터 조회의 실행 계획을 확인하려면 아래를 실행합니다. `vectors`는 `(model, passage)` 기본 키를 사용합니다. 공유 벡터 조회에서 `embedding_refs`는 통계에 따라 `(model, passage)` 기본 키 또는 `embedding_ref_value` 커버링 인덱스를 사용하고, `embedding_values`는 `(model, digest)` 기본 키로 접근합니다.

```sql
EXPLAIN QUERY PLAN
SELECT passage, value
FROM searchable_vectors
WHERE model = 'bge-m3' AND passage IN (SELECT value FROM json_each('[1,2,3]'));
```

## 7. 로컬 종합 답변과 대화

- 단일 질문은 한 번 검색합니다. 비교할 대상이 명확하거나 시간 흐름을 요청하면 규칙 기반 계획으로 최대 세 번 검색합니다. 근거가 충분하면 주제·회신별 중간 사실을 원문과 대조합니다. 최종 답변도 동일한 인용·주체·수치·상충 검증을 통과해야 합니다.
- 앱을 `--model <설치된 Ollama 모델명>`으로 실행하면 **로컬 AI 답변** 버튼이 표시됩니다. 화면에는 질문 분석, 근거 수집, 답변 작성, 인용 검증이 차례로 표시됩니다. `POST /api/answer/stream`은 진행 이벤트와 검증한 최종 답변을 보냅니다. `POST /api/answer`는 JSON 답변에 계속 사용할 수 있습니다. 취소하면 브라우저가 즉시 스트림을 닫고, 서버는 진행 중인 모델 호출이 반환되는 시점에 후속 처리를 중단합니다.
- **새 대화 시작**으로 앞선 대화를 지울 수 있습니다. 서버는 대화별 최근 세 턴을 메모리에만 보관하고 30분 뒤 만료합니다. “그중”, “방금”, “다시” 같은 후속 질문은 현재 보관함 범위에서 다시 확인한 인용과 주제를 먼저 검색합니다.
- 사내 API 답변은 **AI 근거 찾기**로 기존과 같이 발췌문을 확인한 뒤 요청합니다. 로컬 답변의 입력이 길어져도 현재 승인된 모델로 처리할 수 있는 원문을 우선 선택합니다.


## 8. 질의 확장과 근거 예산 설정

- 질의 분해는 `MAILSEARCH_QUERY_REWRITE_MODEL`의 로컬 Ollama 모델을 우선합니다. 이 설정이 비어 있으면 사내 게이트웨이의 답변 모델 또는 `MAILSEARCH_GATEWAY_REWRITE_MODEL`을 사용합니다. 게이트웨이에는 질문과 현지 날짜가 전달됩니다. `MAILSEARCH_QUERY_REWRITE=0`으로 질의 분해를 끌 수 있습니다. 2.5초 안에 결과를 받지 못하면 기존 규칙 기반 검색을 실행합니다. 최대 3개 하위 질의 중 캐시에 없는 항목은 한 번에 임베딩합니다. 추정 필터는 직접 지정한 조건을 우선하며, 적중이 없으면 추정 조건을 풀어 다시 찾습니다.
- 근거량은 `MAILSEARCH_INTERNAL_EVIDENCE_CHARS` 또는 `MAILSEARCH_EXTERNAL_EVIDENCE_CHARS`의 `4000`, `12000`, `24000` 값으로 바꿔 비교할 수 있습니다. 사내 게이트웨이는 `48000`도 지원합니다. JSON 요청의 UTF-8 한도는 `MAILSEARCH_INTERNAL_INPUT_BYTES` 또는 `MAILSEARCH_EXTERNAL_INPUT_BYTES`로 지정합니다.
- 사내 게이트웨이의 기본 입력 예산은 64,000바이트이며 상한은 192,000바이트입니다. 일반 외부 프로필은 기본 5개·각 800자를 검토 화면에 표시하며, 선택한 원문과 질문을 보냅니다. 본문 길이와 JSON 메타데이터에 따라 실제 채우는 글자 수가 달라집니다.
- 사내 게이트웨이의 추가 검색 예산은 복합 질문 10초, 일반 결정 질문 6초입니다. `MAILSEARCH_FOLLOWUP_TIMEOUT`을 초 단위로 지정할 수 있으며 전체 요청에서 생성에 배정한 시간을 먼저 제외합니다. 남은 시간이 2초 이상이면 최대 32개 통합 후보를 한 번 더 재정렬합니다.
- 날짜·보관함 범위가 좁은 FTS 요청은 상위 결과가 부족하면 범위 안의 추가 후보를 조회합니다. 이 경로는 최대 4,096개 메일과 12,000개 구간을 후보로 사용합니다. 관련 회신에서는 결정 표현과 질문 용어를 기준으로 본문·첨부 구간을 선택합니다.

## 10. 최신 결정, 연속 원문과 추가 검색

- 현재·최종 결정을 묻는 질의에는 최대 15%의 시간 가중치와 270일 감쇠 상수를 적용합니다. 비교·이력·과거 시점·종료일 필터가 있는 질의는 관련도 중심으로 조회합니다. 같은 주제·품번에서 확인한 최신 승인·철회는 근거에 포함하되 기존 인용 검증과 상충 판단을 따릅니다.
- 새로 색인하는 구간은 1,100자와 120자 중첩을 사용합니다. 원문 위치가 연속되고 중첩 문자가 일치하면 적중 구간을 포함한 최대 1,800자를 답변에 사용할 수 있습니다. 새 형식은 `sections-v4`이며, 갱신 시 내용이 같은 `sections-v2`·`sections-v3` 구간과 임베딩은 재사용합니다. 구조화 PCF는 기존 셀 단위를 사용합니다.
- 추가 검색은 질의 분해용 모델을 설정한 경우 복합·결정·이력 질문에 한해 사용합니다. `MAILSEARCH_AGENTIC_RETRY=0`으로 끌 수 있습니다. `MAILSEARCH_QUERY_REWRITE=0`은 질의 분해와 공백 진단을 함께 끕니다. 추가 결과의 새 내용에는 답변 근거에서 최대 4자리를 우선 배정합니다. 진단은 최대 2.5초, 진단과 추가 검색 전체는 간단 결정 질문 최대 4초, 복합 질문 최대 6초이며 생성 시간을 남겨 두고 실행합니다. 게이트웨이 진단에서는 질문과 항목별 근거 건수를 사용합니다. 로컬 진단의 원문 발췌는 로컬 모델에만 전달합니다. 답변에 남은 미확인 항목은 적용한 보관함·기간 범위에 대한 결과입니다.
